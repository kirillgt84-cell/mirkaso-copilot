# Mirkaso Copilot

An agentic market assistant built on **Meta Muse Spark** with function calling over
Mirkaso's public market data: scanner signals, sector indices, the macro risk regime
and per-coin derivatives.

Built during the **Meta Global AI Developer Hackathon, Oct 26 – Nov 4, 2026**. Everything
in this repository was written during the hackathon.

## Try it

Run the agent against the real Meta Model API with bundled **synthetic demo data**.
You only need a Meta API key; no access to the private Mirkaso product. By default the
demo shifts every fixture timestamp to the current time, so the data looks live.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e .

export META_API_KEY=...            # your key; read from the environment, never printed
export META_MODEL=muse-spark-1.3   # required, no default; never a "-contributor" model
# export META_API_BASE=...         # optional, defaults to https://api.meta.ai/v1
# export META_PRICE_IN_PER_M=...   # optional: USD per 1M prompt tokens
# export META_PRICE_OUT_PER_M=...  # optional: USD per 1M completion tokens

mirkaso-copilot-demo "Which sectors are strongest right now and is the macro regime supportive?"
mirkaso-copilot-demo "Any unusual BTC or SOL activity?" --show-tools
mirkaso-copilot-demo "How are BTC open interest and funding moving?" --effort medium
mirkaso-copilot-demo "What are the top scanner signals?" --tier guest --json
mirkaso-copilot-demo "Is the macro regime improving?" --fixed-time   # stored 2026-10-26 times
mirkaso-copilot-demo "Any unusual BTC activity?" --verbose           # show why a request failed
mirkaso-copilot-demo "Which sector is strongest right now?" --structured  # server-resolved numbers
```

`python -m mirkaso_copilot.demo ...` works the same way.

| Option | Default | Meaning |
|---|---|---|
| `--tier guest\|starter\|trader\|pro` | `trader` | Plan tier the data is gated for (try `guest` to see masking) |
| `--effort low\|medium\|high` | `low` | Model reasoning effort |
| `--show-tools` | off | Print each tool call with its arguments, `ok` or error code, and latency |
| `--json` | off | Print the full `AgentResult` as JSON: tool call records, usage, warnings and transcript |
| `--fixed-time` | off | Keep the stored timestamps (base time `2026-10-26T12:00:00Z`) instead of shifting them to now |
| `--structured` | off | Return only a **verified** answer (see [Numeric grounding guard](#numeric-grounding-guard)): print its resolved summary and claims and a table of the resolved values (id, value, call alias, tool, path, `as_of`), or the fixed refusal. Also prints `verified: yes/no`, the guard attempts and rejections with their reasons, and usage and latency per phase (tool, `structured_1`, `structured_2`, total). Exit status 1 if not verified. With `--json`, all of these are in the output. |
| `--single-phase` | off | Experiment, implies `--structured`: send the answer schema with every tool-loop request instead of a separate structured request. The API may reject this combination; that shows up as `stop_reason: error` with the HTTP details under `--verbose`. |
| `--verbose` | off | If a model request fails, print the HTTP status and the first 200 characters of the API's error message to stderr (only the error type for connection errors). The key and request headers are never printed. |

What to expect: the model calls one or more tools (several in parallel when the question
needs them), then answers using only the numbers those tools returned and cites their
`as_of` time. After the answer the demo prints `stop_reason`, the number of steps, token
usage (prompt, completion, reasoning, total), total latency and, if both price variables
are set, an estimated cost. The exit status is 0 for a final answer, 1 for any other stop
reason and 2 for a configuration error.

> **The data is synthetic demo data, not real market data.** It lives in
> [`src/mirkaso_copilot/fixtures/`](src/mirkaso_copilot/fixtures/) and is served by
> `FixtureProvider`. Every timestamp is stored relative to the base time
> `2026-10-26T12:00:00Z`. By default all of them (`as_of`, signal times and history
> points) are shifted by the same offset,
> `now - base time`, when the demo starts, so the gaps between them are unchanged and
> answers cite the current time. `--fixed-time`, and `FixtureProvider(fixed_time=True)`
> in tests and evaluations, keep the stored times.
> The fixtures cover 12 scanner signals, 13 sector indices (10 crypto, 3 tradfi), the macro
> regime (score 54.3, Neutral) with 7 days of 15-minute history, and BTC/ETH/SOL derivatives
> with 48 hours of hourly open interest.
> Any other coin returns `not_found`.
>
> The JSON is generated by [`scripts/generate_fixtures.py`](scripts/generate_fixtures.py)
> with a fixed seed (`python scripts/generate_fixtures.py` from the repository root
> rewrites the files identically). A test regenerates the fixtures into a temporary
> directory and fails if they differ from the committed files.

## How it works

```
user ──► host app ──► Muse Spark (Meta Model API, /chat/completions)
            │                 │ tool_calls
            │                 ▼
            │        tools.registry.execute_tool(name, args, provider, ctx)
            │                 │ validate args (pydantic) → gate by tier → downsample
            │                 ▼
            │          DataProvider (adapter) ──► Mirkaso public market data
            ▼
   CallerContext(tier) resolved by the host, never by the model
```

- **Tool definitions** are generated from pydantic parameter models
  (`tool_definitions()`, OpenAI function-calling format). Every schema has
  `additionalProperties: false` and hard caps on limits and windows, so the model
  cannot request unbounded data.
- **One envelope for every result**: `as_of` (UTC ISO-8601), `source_id`, `gated`,
  `gated_fields`, `data`.
- **Errors are structured** (`{"error": {"code", "message"}}`) with fixed messages.
  Exception text, SQL and tracebacks never reach the model; they are logged on the
  host side only.
- **Gating by plan tier** happens in pure functions before the data reaches the model.
  The tier comes from `CallerContext`, which the host app builds from its own session.
  The model cannot raise its own tier through tool arguments.
  See [Tiers](#tiers).
- **Downsampling**: history series are rebucketed to at most 48 points to keep the
  context small.
- `meta_client.MetaClient` is a minimal async client for the Meta Model API
  (`tools`, `tool_choice`, `response_format`, `reasoning_effort` low/medium/high) that
  logs token usage, including reasoning tokens.

## Tools

The model can call exactly four tools:

| Tool | Returns |
|---|---|
| `scanner_get_signals` | Current market-scanner signals for crypto perpetual futures |
| `sectors_get_indices` | Sector indices (crypto and tradfi) |
| `macro_get_regime` | The macro risk regime, its bands and optional history |
| `coin_get_derivatives` | Price, open interest and funding for one coin, with optional open-interest history |

Liquidations are intentionally excluded until a reliable data source exists: the source
behind them is currently unavailable, and a tool over it would report empty totals as
if nothing had been liquidated.

The tool contract is documented in [docs/tools.md](docs/tools.md).

## Agent loop

`mirkaso_copilot.agent.run_agent(question, provider=..., ctx=..., client=...)` runs the
tool-calling loop: it sends the question with every tool definition
(`tool_choice="auto"`), executes all tool calls of a step concurrently, feeds each
result back as a `tool` message, and repeats until the model answers without tool calls.

Limits (`AgentConfig`, all overridable):

| Setting | Default | Meaning |
|---|---|---|
| `max_steps` | 6 | Model requests per run |
| `max_tool_calls_total` | 12 | Tool calls per run |
| `max_total_tokens` | 40000 | Tokens summed over all requests |
| `request_max_tokens` | 3000 | `max_tokens` per request (reasoning tokens count toward it) |
| `structured_max_tokens` | 6000 | `max_tokens` per structured request (and every request in single-phase mode) |
| `reasoning_effort` | `low` | `low`, `medium` or `high` |
| `per_tool_timeout_s` | 15 | Time limit for one tool call |
| `total_timeout_s` | 90 | Time limit for the whole run |

Tool failures never stop the run. A tool error, a tool timeout, arguments that are not a
JSON object, an unknown tool, or a repeat of the same tool with the same validated arguments
(defaults applied, so `{}` and `{"history_days": 7}` match) all
come back to the model as a structured error (`{"error": {"code", "message"}}`), so it
can recover or explain.

`AgentResult` carries `answer`, `stop_reason`, `steps`, a record per tool call (tool
call id, name, args, error code, latency, `source_id`, `as_of`), summed token usage including reasoning
tokens, total latency, `warnings` and the full message transcript. `warnings_detail`
holds opt-in diagnostics for a failed model request (error type, HTTP status and at most
200 characters of the API's error message); it is never sent to the model or logged.

| `stop_reason` | When | `answer` |
|---|---|---|
| `final` | The model answered without tool calls | The model's answer |
| `max_steps` | The step limit was reached | Fixed fallback text |
| `max_tool_calls` | The next step would exceed the tool-call limit | Fixed fallback text |
| `max_tokens` | The token budget was exceeded | Fixed fallback text |
| `timeout` | `total_timeout_s` elapsed | Fixed fallback text |
| `truncated` | The model hit `finish_reason: "length"` | `None` |
| `error` | The model request failed or returned an empty answer | Fixed fallback text |

Fallback texts contain no numbers. Each run also reports usage and latency per phase
in `phases`.

## Structured answers

`run_agent(..., structured=True)` (demo: `--structured`) makes the numbers in an answer
come from the server, not from the model. **The model never writes a number.** It writes
prose with placeholders and, for each placeholder, a pointer to where the value is in a
tool result. The server follows the pointer and substitutes the formatted value:

```json
{
  "summary": "{v1} is the strongest sector with a score of {v2}, {v3} over 24h.",
  "claims": [{"text": "Its strength relative to BTC is {v4}."}],
  "values": [
    {"id": "v1", "call_ref": "t1", "path": "/data/sectors/0/slug", "kind": "text", "decimals": null},
    {"id": "v2", "call_ref": "t1", "path": "/data/sectors/0/sector_score", "kind": "number", "decimals": null},
    {"id": "v3", "call_ref": "t1", "path": "/data/sectors/0/price_change_24h_pct", "kind": "percent", "decimals": null},
    {"id": "v4", "call_ref": "t1", "path": "/data/sectors/0/relative_strength_btc", "kind": "ratio", "decimals": null}
  ],
  "caveats": []
}
```

renders as *"ai is the strongest sector with a score of 74.2, +4.9% over 24h."* and
*"Its strength relative to BTC is 1.41."*

How it works:

1. **Phase A** is the normal tool loop, unchanged.
2. **Phase B**: after the final answer, one more request **without tools** and with
   `response_format` set to the strict JSON schema of `StructuredAnswer`
   ([`answer.py`](src/mirkaso_copilot/answer.py)), with its own token limit
   (`structured_max_tokens`, 6000). The live model spends about two thirds of its
   completion tokens on reasoning even at effort `low`. The request sends the whole
   transcript plus an instruction with the placeholder rules and a **list of every
   executed call by alias**:

   ```
   t1 = sectors_get_indices({"asset_class": "crypto"}) ok, source mirkaso.sectors, as_of 2026-10-27T14:13:02Z
   t2 = macro_get_regime({}) ok, source mirkaso.macro, as_of 2026-10-27T14:13:02Z
   t3 = coin_get_derivatives({"symbol": "NOPE"}) error not_found
   ```

   Each value's `call_ref` names a call by its alias. The model cannot see the real
   tool call ids, and in a live run it filled them with tool names instead. Every
   number, price, percentage, ratio, count and time must be a placeholder. Digits may
   appear in the text only in compact timeframes (`15m`, `1h`, `24h`, `7d`) and in
   asset or sector names. The instruction also limits the answer to 6 claims and 24
   values.

   The schema is deliberately limited to a subset that strict modes accept widely.
   Every object has `additionalProperties: false` and requires all of its properties,
   `kind` is the only enum, and nullable `decimals` is `"type": ["integer", "null"]`.
   There is no `pattern`, `minimum`/`maximum` or `anyOf`/`oneOf`. The id format
   (`^v[0-9]{1,3}$`), the `decimals` range (0–6) and the claim and value limits are
   enforced by pydantic validators when the reply is parsed.
3. **Resolution** ([`resolve.py`](src/mirkaso_copilot/resolve.py), a pure function).
   `call_ref` is matched, in this order, as an alias (`t1`), as a real tool call id, or
   as a tool name that exactly one successful call used. A name used by several
   successful calls is `ambiguous_call_ref`. The value's RFC 6901 JSON Pointer is then
   followed into that call's result envelope, exactly as the model saw it. The value
   must be a number, or a string for `text` and `timestamp`. It is then formatted for
   its `kind`:

   | `kind` | Example |
   |---|---|
   | `usd` | `$152.31`, `$420,000`; from one million on `$56.87M`, `$12.1B` |
   | `percent` | `65.2%`; fields whose name contains `change` or `delta` get a sign: `+4.9%` |
   | `ratio` | `1.41` |
   | `count` | `6,114` (must be a whole number) |
   | `number` | `54.3`, `0.000085`; also signed for `change`/`delta` fields |
   | `timestamp` | `2026-10-26 12:00 UTC` |
   | `text` | the string as is, e.g. `Neutral` |

   `decimals` (0–6) overrides the default precision. For compact USD amounts it applies
   to the shortened number (`$56.9M` with `decimals: 1`). Formatting **never uses
   scientific notation**: `0.000085`, not `8.5e-05`. A value too small for the default
   precision is written out in full (`0.0000000123`).

Resolution errors come back as a typed list:
- `unknown_placeholder`
- `duplicate_value_id`
- `unknown_call_ref`
- `ambiguous_call_ref`
- `tool_call_failed` (the reference names an error result)
- `invalid_pointer`
- `missing_path`
- `wrong_type`

Values that no placeholder uses are allowed and listed in `unused_values`.

**Why this prevents invented numbers:** every number in the rendered text was read from
a tool result by the server, and each one can be traced to its call, path and `as_of`.
The model only chooses *which* value to cite. A wrong pointer gives an error, never a
made-up number. All citable numbers must therefore be in the tool results. That is why
the macro band ranges are a `bands` list in the result and not text in the tool
description (see [docs/tools.md](docs/tools.md)). Numbers the model types into the text
itself are caught by the guard below.

## Numeric grounding guard

With `structured=True`, the run returns **only a verified answer or a fixed refusal**:

```
tool loop ─► structured answer ─► resolve ─► guard ─┬─► verified answer
                                                     └─► 1 regeneration ─► resolve ─► guard ─┬─► verified answer
                                                                                              └─► safe refusal
```

The guard ([`guard.py`](src/mirkaso_copilot/guard.py), pure functions) rejects an
answer for any of these:

- **Resolution errors** (see above).
- **Literal numbers** (`literal_numbers`): digits the model wrote itself, checked on its
  summary, claims and caveats *before* substitution, so the server's formatted values
  are never flagged. A digit is allowed only inside a token that fully matches the
  documented `ALLOWED_TOKEN` regex:
  - a placeholder `{vN}`;
  - a compact timeframe (`15m`, `1h`, `24h`, `7d`, `30d`; lower-case unit only, so `15M`
    is an amount);
  - a name or ticker (`layer-1`, `layer-2s`, `x402-style`, `web3`, `1INCH`,
    `1000PEPEUSDT`);
  - a snake_case field name (`price_change_1h_pct`).

  Everything else is flagged: `$420,000`, `8.5e-05`, `11/13`, `12100000000.0`, `2.5%`,
  times and dates, ordinals (`1st`) and spelled-out timeframes (`24-hour`). Numbers
  written as words ("eleven") are not detected.
- **Advice wording** (`advice_phrases`): a conservative list of English phrases such as
  "you should buy", "I recommend", "go long", "good time to", "guaranteed", "will go
  up", "price target" and "financial advice". Disclaimers such as "this is not financial
  advice" are allowed. Signal labels like "a LONG signal" are not advice. The check is
  injectable: `run_agent(..., output_guard=fn)` takes any callable from text to a list
  of offending phrases and replaces the default. The private Mirkaso product plugs its
  existing output guard in there.
- **Invalid answers**: a reply that is not valid JSON for the schema, has more than 6
  claims or 24 values, or was cut off at the token limit.

If the first answer is rejected, **one regeneration** follows. It is a new structured
request with the rejected reply and a short correction message listing the concrete
problems, for example:

```
Your previous answer was rejected for these problems:
- v4: unknown_call_ref (No call 't9'.)
- literal number '8.5e-05' in claim 1; use a placeholder
Fix them and give the complete answer again as JSON that matches the response schema, following the same rules.
```

Pydantic error messages are passed on without the reply text. If the regeneration is
rejected too, the run returns a **safe refusal**: *"I couldn't produce a verified answer
for this question. Please try again or ask more specifically."* That text contains no
number. `stop_reason` stays `final`, `verified` is `False` and `refusal_reason` is one
of these:
- `guard_failed`
- `structured_invalid`
- `structured_length`
- `structured_request_failed` (an HTTP error, which is not retried)
- `timeout` (the whole structured phase stays within `total_timeout_s`)

A structured run **never falls back to the unverified phase A text**. That text stays in
the transcript only.

Metrics on `AgentResult`:

| Field | Meaning |
|---|---|
| `verified` | `True`, `False`, or `None` for a run without `structured=True` |
| `refusal_reason` | Why a structured run was refused, else `None` |
| `answer` | The rendered verified text, or the refusal |
| `structured`, `resolved` | The verified answer and its resolution; `None` when refused |
| `resolution_errors` | Resolution errors of the last attempt, for diagnostics |
| `guard_attempts` | Structured answers checked (1 or 2) |
| `guard_rejections` | How many of them were rejected |
| `rejected_reasons` | One list of problem lines per rejected attempt |
| `phases` | Usage and latency per phase: `tool`, `structured_1`, `structured_2` |

`usage` and `latency_ms` remain the totals over all requests, regenerations included.

**Single-phase experiment** (`structured_mode="single_phase"`, demo `--single-phase`;
default off): the schema is sent with the tools in every request of the loop, and the
final message is parsed as the structured answer, which saves one request. The aliases
`t1`, `t2`, ... are explained in the system prompt, since no call list can be shown in
advance. A regeneration uses the two-phase request, with the call list. If the API
rejects tools together with `response_format`, the run ends cleanly with `stop_reason:
error`, and `--verbose` shows the HTTP details.

## Tiers

Gating uses four public tiers, lowest first:

```
guest < starter < trader < pro
```

| Tier | Scanner | Sector `sector_score_delta_24h` |
|---|---|---|
| guest | masked | hidden |
| starter | masked | visible |
| trader | full fidelity | visible |
| pro | full fidelity | visible |

The host application maps its own plan names to these four tiers when it builds
`CallerContext`. The mapping is not part of this repository. A tier that is not one of
the four is treated as `guest`, so a mapping mistake fails closed.

## Boundary: what is in this repo and what is not

| In this repository (new, open, MIT) | In the private Mirkaso product (not here) |
|---|---|
| Tool definitions, parameter schemas and caps | Data ingestion pipelines |
| Result envelope and error model | Database schema, SQL and storage |
| Tier gating and downsampling (pure functions) | Scanner and scoring logic |
| `DataProvider` protocol, a test fake and a synthetic-data `FixtureProvider` | The production `DataProvider` implementation |
| Meta Model API client | Accounts, billing and tier resolution |

The private product plugs in by implementing `mirkaso_copilot.providers.DataProvider`.
This repository contains no credentials, no internal table names and no proprietary
signal logic.

## Development

Requires Python 3.11+.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
ruff check . && ruff format --check .
pytest
```

Tests use a fake provider and make no network calls.

To call the Meta Model API, copy `.env.example` to `.env` (git-ignored) and set
`META_API_KEY`, `META_MODEL` (e.g. `muse-spark-1.3`) and optionally `META_API_BASE`.
The code has no default model.

> **Never use a model ID ending in `-contributor`.** Those variants may be trained on
> the data you send. Use only the standard model.

The client reads these
from the process environment only.
